# Gid Tourist — перевірка годин послуг, бронювань і логотипів

## Що змінено

1. У картці послуги туриста виправлено порядок шарів: чітка фотографія над розмитим фоном. Дизайн та геометрію картки не змінено.
2. У клієнтській картці закладу прибрано штучні внутрішні білі відступи навколо логотипа; логотип заповнює відповідну верхню область.
3. При натисканні «Бронювати» передається точний `placeId` та `service.id`, а фото береться з опублікованої послуги (`/partner/services/public/:placeId`), не з демонстраційних зображень. Великий base64-файл не дублюється у `sessionStorage`.
4. Партнер може вибрати **кожен день тижня** й обмежити години, доступні для початку послуги. **Необрані дні** отримують усі слоти за основним часом роботи, тривалістю, інтервалом і перервами. День можна повністю вимкнути або повернути «Усі години».
5. Backend записує `day_slots` в наявне `booking_resources.working_hours` (JSONB), перевіряє дозволені години при кожному бронюванні та не пропускає зайняті години. Нової SQL-міграції не потрібно.
6. Для збережених раніше послуг, у яких `bookingEnabled=true`, але немає рядка календаря, Backend може безпечно відновити відсутній `booking_resources` через ідемпотентний `INSERT ... ON CONFLICT DO NOTHING`. Відсутність збережених налаштувань не замінюється вигаданим графіком.
7. У партнерському кабінеті пункт «Бронювання» перший. Екран розділяє нові заявки, підтверджені та історію, оновлює дані автоматично кожні 30 с. Зайняті години відображаються на вибрану дату; підтвердження/скасування одразу оновлює календар.

## Сценарії ручної перевірки

1. **Partner → Послуги → редагувати послугу**. Увімкнути онлайн-бронювання, задати роботу 09:00–18:00, тривалість 60 хв, інтервал 60 хв, гостей 2, ціну. Відкрити **Пн**, вимкнути 10:00, залишити 09:00 і 11:00. На **Вт** нічого не змінювати. Натиснути **Зберегти**; переконатися, що немає помилок.
2. **Турист → Послуги закладу → конкретна послуга**. Зображення у деталях різке, не перекрите розмитим фоном. Натиснути **Бронювати**. Показується **назва і фотографія тієї ж послуги**, а не фото іншого закладу.
3. Відкрити дату понеділка: доступні лише явно дозволені години, які ще не зайняті. Відкрити вівторок: доступні всі години 09:00–17:00 за умови відсутності бронювань. Перевірити невірний/минулий час: створення не проходить.
4. Надіслати запит клієнта на 09:00, перевірити, що слот 09:00 зник із доступних для інших, а в **Партнер → Бронювання → Очікують рішення** з'явилася заявка. Натиснути **Підтвердити**. Переконатися, що в календарі година лишається зайнятою. Для іншої заявки натиснути **Відхилити** — після оновлення слот повернеться.
5. У профілі туриста відкрити **Мої бронювання**. Заявка має відображати актуальний статус. У партнері перевірити розділ **Історія бронювань**.
6. Відкрити клієнтську картку закладу з QR, перевірити логотип і фото послуг на телефоні; зображення заповнює виділену область.

## Безпечні SQL-запити Railway / PostgreSQL (тільки читання)

```sql
-- Фактичні налаштування послуг у картці закладу.
SELECT p.id AS place_id, p.name AS place_name,
       s.service->>'id' AS service_id, s.service->>'name' AS service_name,
       s.service->>'bookingEnabled' AS booking_enabled,
       s.service->>'timeFrom' AS service_from,
       s.service->>'timeTo' AS service_to,
       s.service->'daySlots' AS per_weekday_slots
FROM places p
CROSS JOIN LATERAL jsonb_array_elements(COALESCE(p.details->'services','[]'::jsonb)) AS s(service)
WHERE p.name ILIKE '%Puri%' OR p.name ILIKE '%Пурі%';

-- Реальні ресурси календаря, створені з цих налаштувань.
SELECT r.id, p.name AS place_name, r.name AS service_name,
       r.active, r.duration_minutes, r.capacity,
       r.working_hours->'days' AS available_days,
       r.working_hours->'day_slots' AS individual_day_slots,
       r.working_hours->>'from' AS from_time,
       r.working_hours->>'to' AS to_time
FROM booking_resources r JOIN places p ON p.id = r.place_id
WHERE r.id LIKE 'service:%' ORDER BY p.name, r.name LIMIT 100;

-- Бронювання й статуси, що блокують/звільняють час.
SELECT b.id, p.name AS place_name, r.name AS service_name,
       b.starts_at, b.ends_at, b.status, b.party_size
FROM bookings b JOIN places p ON p.id=b.place_id
JOIN booking_resources r ON r.id=b.resource_id
ORDER BY b.created_at DESC LIMIT 50;
```

## Межі перевірки

Синтаксис змінених TS/TSX-файлів і ізольований календарний алгоритм перевірені. Збірку `next build` / `nest build` і підключення до робочої Railway PostgreSQL необхідно перевірити на деплої. Відновлення календаря відбувається **лише** для послуг, у яких на сервері фактично збережено `bookingEnabled=true`; жоден тестовий графік для інших послуг не створюється.
